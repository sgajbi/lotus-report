# Report Job Propagation Context

Report binds source collection to the persisted job's accepted correlation and trace identity.
The durable worker previously transmitted its pass context through ambient clients while storing
the accepted job identity in upstream-call lineage. A source log could therefore disagree with
the identifiers Report claimed for that call.

`bind_propagation_context` in `src/app/observability.py` uses ContextVar tokens and restores them
in `finally`. `ReportJobExecutionService.execute_job` loads the persisted job, then binds its
correlation/trace across capture, render and owner-wait outcomes. The entire
`ReportingReadPortfolioReviewInputProvider.collect_for_job` also binds that identity, including
optional AI enrichment. This covers direct API regeneration and recollecting replay, which can
enter the provider without the worker executor. Nested scopes restore the enclosing job scope
before execution restores its original caller scope.

| Fact | Meaning and behavior |
| --- | --- |
| Job correlation/trace | Persisted acceptance facts used for source propagation and recorded call lineage; retries preserve them |
| Worker-pass correlation/trace | Operational pass identity restored after every job, including failure and cancellation |
| Request ID | Existing ambient operational request identity; the helper does not replace it with a job ID |
| Work item and attempt | Existing durable work-item-to-job relationship, lease and attempt facts; unchanged by context binding |
| Tenant/caller/actor/authority | Existing admitted application facts and explicit client arguments; context binding does not change authorization |

Blank or absent persisted correlation/trace is refused with internal
`propagation_identity_missing` before source calls. The boundary does not generate a diagnostic
identifier and then record a different missing identifier as though it were transmitted. The
ordinary worker execution-failure path and capture-failure mapping retain responsibility for
that outcome; this change does not repair historical rows or snapshots.

Core supplies explicit job correlation and uses ambient trace; Performance, Risk and AI use the
bound ambient propagation context. Their existing retry/poll operations inherit the same scope.
Render and Archive already receive explicit correlation/trace. Their clients do not uniformly
forward `X-Request-Id`, so a worker-pass request header is not claimed for every downstream owner.
Retained-snapshot replay and rerender preserve their existing command identity and perform no
new source collection. Regeneration creates a new job with its own accepted command identity.

Unit regression controls exercise exact propagation values and restoration on success, source
refusal, capture/render exceptions, owner waiting, cancellation during an awaited source call,
two adjacent jobs, nested scopes, concurrent jobs and missing identity. These in-process controls
do not establish actual source HTTP/PostgreSQL lineage joins. A native worker wire proof must
join actual response hashes, wire identity, durable upstream-call rows and their job/work-item
facts before end-to-end qualification.

Context propagation is distinct from exported traces, authenticated IAM and audit sink delivery.
It does not establish source arithmetic, Render-generated bytes, Archive custody, collector/span
links, alert delivery, capacity or canonical UI readiness. Metrics retain bounded labels; job,
tenant, correlation, trace and request identifiers remain outside Prometheus labels.
